## FAILURES, worst first

### F1 — `fk_downgoing.separate`: quadrant mask was not Hermitian; energy silently discarded  · FIXED

`np.fft.fftshift(np.fft.fftfreq(n, d))` on an axis of EVEN length carries
`-k_Nyquist` but not `+k_Nyquist`, so the conjugate partner of the Nyquist bin
is **itself**. The pointwise quadrant mask `0.5*(1 + sign(k)*sign(f))` therefore
assigned a bin and its own partner *opposite* values. The masked spectrum was not
Hermitian, `np.real()` threw the difference away, and the two panels were each
distorted along the whole k-Nyquist row and f-Nyquist column.

Measured on a 367×701 synthetic (`audit_test_fk.py` A4/A5), before the fix:

```
max|imag| / max|real|                    = 1.886e-03      (should be ~1e-16)
mask asymmetry max|m(k,f) - m(-k,-f)|    = 1.000          (should be 0)
non-Hermitian bins                       = 636 of 257,267 (the k-Nyq row + f-Nyq col)
energy in those bins                     = 2.968e-05 of the total spectrum
```

The round-trip check `down + up == input` **passed throughout** (4.4e-16) and so
did **not** catch this: the two panels' imaginary parts cancel exactly in the
sum even though each panel individually is wrong. That is why a round-trip test
alone is insufficient here.

Fix: `_hermitian()` averages each mask bin with its conjugate partner before use,
splitting the Nyquist row 50/50 (direction is undefined there) and preserving
`m + (1-m) == 1`. After the fix:

```
max|imag| / max|real|   = 4.255e-16   PASS
mask asymmetry          = 0.000       PASS
non-Hermitian bins      = 0           PASS
round trip              = 7.772e-16   PASS
```

`separate()` now **raises** if the imaginary residue exceeds 1e-9.

**Invalidated:** `fk_downgoing_deep_dense`, `_deep_cm`, `_deep_pub`, `_nano`
`.{npz,png,txt}` as written at 16:27–17:21. Regenerated by `audit_job.sbatch`.
The effect on the headline ratios is small (3e-5 of spectral energy) but the
panels were not what they claimed to be.

### F3 — `read_records` held three full float64 copies; `target_bytes` budgets were 2× optimistic  · FIXED

`deep_timeseries.block_spectra` sizes its channel groups as
`target_bytes / (total_n * 4 * 3)`, i.e. it budgets 12 bytes per sample per
channel. `read_records` returns **float64** and, before returning, held the
per-file block list, the `np.concatenate` result and the `[inverse]` fancy-index
copy simultaneously — 24 bytes/sample. Measured directly with `tracemalloc` on a
synthetic HDF5 set:

```
OLD read_records: returned 29.3 MB, traced peak 87.9 MB  (3.00x)
NEW read_records: returned 29.3 MB, traced peak 33.0 MB  (1.13x)
```

A real 4 h deepC block is 240 records × 60000 samples × 343 channels = **36.80 GB
at float64** for the whole block; at the production `per_group = 22` the read is
2.79 GB against a 3.70 GB budget, where before it was 7.40 GB. This is the
mechanism behind the "OOM-killed 12 of 16 array tasks at 64 GB" the coordinator
was working around at a higher level.

Fix: `read_records` now takes record lengths from each dataset's `.shape`
(HDF5 metadata, no data read), preallocates the output once, and writes each
file straight into `out[order, at:at+n]` so no permuted intermediate is ever
materialised. Values are bit-identical (`audit_test_readrecords.py` R6, max abs
diff 0.000e+00) and the descending-channel return-limb path still works (R2).

With this, `block_spectra`'s existing `4*3` formula becomes honest — the binding
term is now the float64 return alive next to its float32 copy, exactly 12
bytes/sample (`audit_test_correlator.py` C5, 1.00×). Observed effect: the deepC
array (job 40078776) is running **16 of 16** tasks at a 32 GB request, where the
previous attempt lost 12 of 16 to OOM at 64 GB.

### F4 — the chunked/whole equivalence gate could not distinguish an honest edge effect from a real bug  · RESOLVED BY REDESIGN

The first version of the streamed `block_spectra` split the block in **time**.
Chunking a windowed accumulation is exact for the sum itself, and the tail carry
and strain-rate carry were both arithmetically **correct** — with the
running-abs-mean disabled the two paths agreed to `0.000e+00`
(`audit_test_correlator.py` C4a). But the 0.1 s centred running-abs-mean saw
`mode="nearest"` padding at each join, so the honest residual was:

```
19 joins  ->  rel diff 1.957e-03
 4 joins  ->  rel diff 1.004e-03
 2 joins  ->  rel diff 7.868e-04
```

against a declared gate of `< 1e-3`. **The gate failed on its own correct code.**
Worse, a mutation test injecting a *real* bug (deleting the strain-rate carry, so
one sample per chunk is wrong) produced `3.343e-03` — only 1.7× the honest
residual. No tolerance can separate those, so the test had essentially no power.

The coordinator then re-split by **channel group** instead of time, which has no
joins at all. Re-verified:

```
C4a  grouped == ungrouped, per_group 1 : rel diff 0.000e+00, windows 79/79/79   PASS
C4a  grouped == ungrouped, per_group 3 : rel diff 0.000e+00, windows 79/79/79   PASS
```

Mutation sensitivity is now excellent (each mutation applied to a re-`exec`'d
copy of the module and compared against the real one):

```
1e-7 amplitude perturbation           -> detected, rel 1.147e-07
drop the last window                  -> detected, windows 79 vs 78
reverse receiver order within a group -> detected, rel 1.069e+00
```

One weakness found in that mutation set and fixed in `audit_test_correlator.py`:
with the test's original `target_bytes` the sizing formula gave
**`per_group = 1`**, which makes every within-group ordering mutation vacuous
(reversing a one-element list is a no-op, and it initially reported `rel = 0.0`
as a false PASS). The test now asserts that at least one case has `per_group > 1`.

Also note: `per_group` silently collapsing to 1 is a **performance** cliff, not
just a test artefact — it re-reads the source channel and re-walks every file
once per receiver (342 full passes over a 4 h block).

### F5 — `moveout_energy`'s down/up ratio is not an energy ratio and is non-monotonic  · MITIGATED

`fk_downgoing` reported `downgoing / upgoing = 1.564 … 1.972` (Deep) and `0.985`
(Nano) and read those as directionality. But `moveout_energy` normalises every
trace by its own median envelope, so the ratio is scale-free — the script's own
comment says it "is blind to uniform scaling", yet the ratio is still quoted as
if it measured relative energy.

Calibrated against **known** input at the exact production geometry
(367 traces × 701 lags, 5–20 Hz, with an incoherent noise background so the
per-trace median envelope behaves as it does on real data):

```
true down:up   ->  reported e_down/e_up   (taper 6 | brick wall)
  pure down    ->     5.905              |     5.919
  4 : 1        ->     6.515              |     6.499
  1 : 1        ->     6.058              |     6.475
  1 : 4        ->     2.229              |     2.255
  pure up      ->     1.071              |     1.096
```

Two things follow. The statistic is **non-monotonic** — 4:1 scores *higher* than
pure downgoing — so it cannot be inverted to a physical ratio. And a **perfectly
balanced 1:1 wavefield reports 6.06, not 1.0**, because the metric evaluates the
causal trajectory `t = +z/v` and the upgoing panel has almost nothing there by
construction. On this scale the published 1.56–1.97 sits at roughly **19 % of the
range between pure-upgoing (1.07) and pure-downgoing (5.90)** — i.e. it is a
*weak* directionality result, not a strong one.

Fix: `fk_downgoing` now also reports, and saves as `energy_ratio`, the plain
quadrant energy ratio `sum(down²)/sum(up²)`, which has none of this ambiguity,
and labels the old number `<- NOT an energy ratio`.

### F6 — `separate()` silently swapped the quadrants on a descending position axis  · FIXED

`dz = median(diff(positions))`. On the Deep return limb TVD decreases with
channel index; a caller passing the raw (unsorted) TVD gets a **negative** `dz`,
which negates the k axis and exchanges the two quadrants — the "downgoing" panel
would then contain the upgoing wavefield, with no error and no warning. The
section scripts do `argsort` first, so no product is affected, but nothing
enforced it. `separate()` now raises on `dz <= 0`.

### F7 — `deep_cc_steps` was the only script still in float64, and allocated three temporaries where one would do  · FIXED

`deep_cc_steps.main` held `raw`, `rate` and `normed` at full size simultaneously
and never converted to float32. `differentiate()` allocated `np.zeros_like(x)`
*and* a `np.diff` temporary *and* — because `fs` is a Python float — promoted a
float32 array to float64 for the product. `ram_normalise()` allocated
`np.abs(x)`, `w` and the quotient, and its floor was built from
`np.finfo(np.float64)`, a Python float that numpy promotes, so a float32 caller
silently got a float64 result back.

At `--nfiles 60` with ~295 channels at the measured 1000 Hz that is 8.5 GB per
full-size array and a peak near **42 GB against the job's 64 GB request**.

The float32 question was settled by measurement rather than assumed, because
differencing large numbers in float32 is exactly the cancellation trap worth
worrying about. `audit_job2.sbatch`, both arms:

```
raw int32 range          -1547064 .. 1853043      (float32 is exact below 2^24 = 16777216)
float32 spacing there    0.0312 counts
|sample-to-sample diff|  median 109, p05 10, p95 400 counts
                         -> quantisation is 0.03% of the median difference
strain rate:    rel RMS error of the float32 path  = 0.000e+00
cross-spectra:  rel diff float32 vs float64        = 0.000e+00
VERDICT: float32 conversion is SAFE here
```

It is not merely safe, it is **exact**: every int32 value in range is
representable in float32, so the conversion and the subsequent difference are
both lossless. This also retroactively validates the float32 conversion that
`deep_record_section`, `deep_section_depth`, `deep_zerolag_vs_stack`,
`deep_timeseries` and `nano_long_stack` were already doing unexamined.

Fixes: `main()` converts to float32 straight after `read_records`;
`differentiate()` uses `np.subtract(..., out=)` and a dtype-matched scalar (one
array live instead of three); `ram_normalise()` takes eps from the input dtype
and is dtype-preserving — which additionally makes it agree with the engine,
whose floor is already float32 eps. Verified exact (`audit_test_correlator.py`
C6/C6b):

```
C6  differentiate exact and dtype-preserving (float32)  max abs diff 0.000e+00
C6  differentiate exact and dtype-preserving (float64)  max abs diff 0.000e+00
C6b ram_normalise float32 == float64                    max rel diff 6.272e-08
```

Memory after the fix, **measured, not projected** — `sacct -j 40081870`:

```
State COMPLETED, Elapsed 00:03:50, MaxRSS 51372648K = 49.0 GB, ReqMem 64G
  raw shape (295, 3600000) float32     (was float64, i.e. 8.5 GB -> 4.25 GB/array)
```

**49 GB against a 64 GB request is still tight**, and my own pre-run estimate of
"~21 GB after the fix" was wrong: it counted the three named arrays and missed
that the ablation ladder re-runs `ram_normalise(raw, fs)` while `raw`, `rate` and
`normed` are all still referenced, that `--verify` adds `raw.copy()` plus the
engine's own `rate`/`absolute`/`weights`, and that glibc does not return freed
arenas to the OS so MaxRSS records the accumulated high-water mark. The same
arithmetic in float64 comes to roughly 90 GB, i.e. the pre-fix script would not
have fitted in its own request at all.

Recommended follow-up (not done): free `raw` and `rate` before the ablations, or
recompute each ablation from a re-read rather than holding all three stages live.

Re-run under `deep_cc_steps_job.sh`, which carries `--verify`. That check got
**stronger**, not weaker:

```
=== verification against ambient_lellouch2019_exact_stack.py ===
  strain-rate + RAM stage: max abs diff 0.000e+00 (relative 0.000e+00)
```

The compact correlator is now **bit-identical** to the authoritative engine.
Before, the compact path ran in float64 and the engine in float32, so the two
could only agree to ~1e-7 and the tolerance was set at 1e-5. They are now the
same arithmetic.

## Findings that are not code bugs, but do bound the published numbers

### N1 — the 6-cell taper is not disjoint across most of the analysis band

The taper is a fixed number of **cells** and a cell is `1/aperture`, so its width
in physical wavenumber is set by the array length. At the production geometry
(367 traces × 2.0419 m, ±0.35 s) the fraction of a 1675 m/s wave kept by the
correct panel is:

```
 5 Hz 0.72   7 Hz 0.85   9 Hz 0.93   11 Hz 0.98   13 Hz 1.00   15-19 Hz 1.00
```

1.0 is disjoint, 0.5 is no separation at all. So below ~13 Hz the mask is still
inside its own transition and the two panels overlap; at 5 Hz, 28 % of a
downgoing wave lands in the "upgoing" panel. Over half of a 5–20 Hz band by
octave sits in that region.

`fk_downgoing` now prints this table before it prints any ratio and saves it as
`contrast_f` / `contrast_kept`. Either run with `--taper-cells 0` (the brick
wall, which is disjoint everywhere off the axes) or restrict the band to
13–20 Hz — which is also where `deep_timeseries`'s docstring says the Deep mode
is strongest.

### N2 — the 2-D FFT is unwindowed, and the arrival runs off the lag edge

`separate()` applies no window in z or t before `fft2`. Wrong-panel **energy**
leakage is small and acceptable (13–20 Hz: 1.5 % / 0.8 %; 5–20 Hz: 2.9 % / 1.4 %,
`audit_test_fk.py` A3), but the **peak-amplitude** leakage is 20× larger (0.41–0.55)
because the leaked energy concentrates in edge ringing. Two causes, isolated:

```
pure upgoing, 13-20 Hz, energy leaked into the downgoing panel
  production geometry (367 traces, arrival truncates)   0.0211
  contained (200 traces, arrival inside the window)     0.0194
  contained + Tukey(0.25) in z and t                    0.0097
  production geometry + Tukey(0.25)                     0.0052
```

At 1675 m/s the moveout line leaves the ±0.35 s window at 586 m, so the last
~22 % of the 750 m section has no arrival inside the window at all yet still
contributes a hard truncation edge. A Tukey taper cuts the leakage 4×. Not
applied, because it changes every existing product; recorded as the recommended
next change.

### N3 — Nano diagnostics and Nano analysis run at different sample rates

`nano_find_wellhead.py` reads with `fmax=200` and gets **fs = 500 Hz**;
`nano_long_stack.py` and `nano_ambient_cc.py` read with `fmax=100` and get
**fs = 250 Hz**. Confirmed from the run logs. This is defensible — the wellhead
diagnostic needs the 40–100 Hz band that `fmax=100` would have removed — but it
means the diagnostic and the analysis are not looking at the same data, and it is
undocumented.

The sign convention is now pinned analytically rather than guessed: numpy's
`exp(-2πi(kz+ft))` puts `u(z,t) = w(t - z/v)` on `k = -f/v`, so **downgoing is
`k*f < 0`**. The production runs all chose `negative-k`, which under the old
(mis-named) labelling is that same quadrant — so **the existing runs were not
sign-inverted**. But the choice was made by an energy heuristic that only works
when the arrival lands exactly on `t = z/v_ref`; it is now made analytically and
the heuristic is retained only as a cross-check that warns on disagreement.

### E — the pattern sweep

- **Mutable / module-array default arguments.** An AST sweep of all nine files
  found three: `ram_normalise(..., ram_s=RAM_S)` (a float, harmless),
  `moveout_curve(..., velocities=V_GRID)`, and `per_velocity_null(..., n=NULLS)`.
  `moveout_curve`'s is the exact pattern that broke
  `ambient_lellouch2019_exact_stack` (`velocities=VELOCITY_GRID_M_S` ignoring
  `--velocity-min/max`). **No live bug** — all three `V_GRID` definitions
  (`deep_cc_steps`, `nano_long_stack`, `nano_ambient_cc`) are the identical
  `np.arange(300.0, 6000.1, 25.0)`. But `per_velocity_null` called
  `moveout_curve` *without* forwarding `velocities` while sizing its output from
  the module `V_GRID`, so a caller scoring on a different grid would have been
  compared against a null built on the wrong one. **Fixed**: `per_velocity_null`
  now takes and forwards `velocities`.
- **Filters applied twice.** None found. The Nano path applies a 1–100 Hz (or
  1–200 Hz) filter at read time and 5–20 Hz after stacking — different bands, not
  a double application.
- **Bandpass corners above Nyquist.** None live. Deep and Nano both run well
  inside Nyquist for 5–20 Hz and 15–30 Hz. The one unguarded corner is R4 above.
- **`np.diff` without a matching dt.** One, `nano_find_wellhead.py:79`
  (`detrend(np.diff(x, axis=1), axis=1)` with no `* fs`). Everything downstream
  is a ratio or a comparison against a similarly scaled median, so the missing
  1/dt cancels; cosmetic only. Every other differentiation multiplies by `fs`.
- **`detrend` on the channel axis.** None. The only `detrend` call uses `axis=1`,
  which is time for these `(channel, time)` arrays.
